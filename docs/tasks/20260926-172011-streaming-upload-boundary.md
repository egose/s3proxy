# Unsupported AWS Streaming Upload Boundary

Created: 2026-09-26 17:20:11 (local timestamp).

## Objective And Evidence

Continue the [request-boundary review](20260926-170047-request-boundary-health.md) with one new independently verifiable defect. s3proxy terminates client S3 requests and rebuilds backend-authorized requests; ordinary object bytes must not be confused with an unsupported AWS streaming envelope. V1 intentionally supports ordinary single-request uploads, not AWS per-chunk signature/checksum-trailer processing.

The focused read-only review covered request header forwarding, payload validation, classifier, body replay/streaming, and relevant prior tasks. `noneAuthenticator` skips payload-shape checks, while the backend strips inbound payload hash/decoded-length headers, re-signs with `UNSIGNED-PAYLOAD`, and forwards the original `aws-chunked` body. Source inspection establishes the unsupported forwarding path, not corruption against a real S3 provider. Regression-first local state/capture tests are required below.

Deduplication: prior auth tasks validate signed payload hashes; compression work protects response bytes; prior replay work bounds buffering. None enforces AWS streaming format rejection independently of authentication. The latest query/probe tasks address distinct request interpretation boundaries. No second finding was promoted without sufficient evidence.

### Task PAYLOAD-01: Reject Unsupported AWS Streaming Formats Before I/O

Status: completed

Kind: defect

Priority: P2 — unsupported encoded bodies can be rebuilt into backend-authorized ordinary PUTs.

Suggested agent: S3 payload/HTTP boundary implementer.

Dependencies: none.

Primary ownership: a small shared request-payload validation helper if useful, `internal/httpapi/handler.go`, `internal/auth/verify.go`, `internal/dispatch/dispatch.go`, `internal/backend/s3/client.go`, focused tests and payload/API/operator documentation.

Finding: in `auth = "none"`, streaming payload markers do not encounter `validatePayloadHashClaim`; classification accepts PutObject. Backend body preparation streams/replays the envelope without decoding it, filters the original `X-Amz-Content-Sha256`/`X-Amz-Decoded-Content-Length`, and re-signs as `UNSIGNED-PAYLOAD` while retaining Content-Encoding and S3 trailer declarations. SigV4 mode rejects streaming hash sentinels, but an aws-chunked Content-Encoding with an otherwise accepted hash can also evade a format-specific check. The gateway cannot honor the original chunk signatures or trailer semantics after this rebuilding.

References:

- `internal/auth/auth.go` (`noneAuthenticator.Authenticate`).
- `internal/auth/verify.go:423-438` (`validatePayloadHashClaim`).
- `internal/s3ops/classify.go:83-96` (PUT classification).
- `internal/backend/s3/client.go` (`prepareSourceBody`, `shouldForwardHeader`); `internal/backend/s3/signer.go` (UNSIGNED-PAYLOAD).
- `internal/dispatch/dispatch.go` (replay before fan-out).
- `website/docs/api-reference.md:61` (streaming sentinels unsupported); backend operation-boundary tests currently omit these formats.

Requirements:

1. Define one reusable metadata-only rejection rule for unsupported AWS payload formats: Content-Encoding contains the case-insensitive `aws-chunked` token; any X-Amz-Content-Sha256 value uses a `STREAMING-` sentinel; or a nonempty X-Amz-Trailer declaration requests unsupported S3 trailer processing. Inspect repeated header values and case-insensitive names without rewriting request headers or reading/sniffing the body. Distinguish token membership from substring matching and preserve ordinary encodings. Specify handling of whitespace/case consistently in tests/docs.
2. Apply it at HTTP ingress after strict query validation and before auth/payload body verification/replay/routing/dispatch. Return safe S3 `501 NotImplemented` without reflecting header values. This intentionally changes former auth failure for streaming sentinels to consistent format rejection; malformed queries still take 400 precedence. Eligible ordinary health probes retain their established behavior.
3. Enforce the same unsupported-format boundary for standalone SigV4 verification, direct dispatcher calls before fan-out replay, and direct backend execution before GetBody/body preparation/signing/network. Use a fixed typed/sentinel error with no raw header data; keep the small helper independent of auth/config/addressing.
4. Do not infer framing from byte contents or reject ordinary HTTP `Transfer-Encoding: chunked`, Content-Encoding gzip, regular checksum headers, or opaque object bytes merely resembling AWS chunks. No decoder/normalizer workaround and no silently stripping the framing indicators to force an upload through.
5. Regression-first: demonstrate unsupported bytes reached a local capturing/stateful backend before the fix in auth-none and appropriate signed/presign encoding-only variants. Show source markers replaced/removed where relevant; state that the local backend is a test fixture, not S3 provider conformance evidence.
6. Cover known/unknown lengths, existing GetBody callbacks, fan-out and continued routes, and malformed-query precedence. Direct entry points must reject without consuming/replaying sources or changing stored state. Preserve 413/503 replay semantics for supported bodies.
7. Update README/API/request examples or operations docs as appropriate: how unsupported streaming formats fail, their distinction from HTTP chunking/gzip, and practical advice to use ordinary supported single-request uploads. Avoid unverified SDK option prescriptions.
